Room Fts4：全文搜索替代 SQL LIKE

Oct 20th, 2026 12:00 am

本文译自「Scaling Android Search: Room @Fts4 vs SQL LIKE」，原文链接https://proandroiddev.com/scaling-android-search-room-fts4-vs-sql-like-b2a8232cbd12，由Oğuzhan Aslan发布于2026年10月11日。

本文将深入探讨如何使用 Android Jetpack Room 实现全文搜索索引、倒排索引和微秒级查询基准测试。

在为 Android 应用程序构建搜索功能时——无论是查询离线优先的收件箱、笔记目录、文档缓存还是电子商务目录——几乎所有开发者都从相同的查询开始：

它直观易用，无需修改任何表结构，开箱即用。在早期开发阶段，即使本地数据库只包含 25 行虚拟数据，搜索查询也能立即返回结果。测试通过，用户界面流畅，该功能顺利发布。

然后，现实给了我们当头一棒。

随着用户积累数月的多行电子邮件、笔记或缓存数据（从数百条记录攀升至数千条记录），投诉开始纷至沓来：

  • 在搜索框中输入文字时出现按键延迟。
  • 画面出现丢帧和主线程微卡顿。
  • 进行大量搜索操作时，电池电量消耗明显。

为什么在开发阶段感觉运行速度极快的操作，在真实数据量下却会不堪重负？要理解这一点，我们必须深入了解 SQLite 的查询规划器。

为什么 SQL LIKE 在大规模场景下会失效

在关系数据库中，开发人员依靠索引（B 树）来将查找时间复杂度控制在 O(log N) 以内。例如，如果你查询：

SQLite 可以在 sender 上使用标准的 B 树索引，因为它知道前缀。

然而，用户很少只使用前缀进行搜索。实际的全文搜索需要子字符串匹配：在主题或段落中查找任意单词。这迫使查询语句以通配符开头：

警告：一旦查询语句包含前导通配符（%query%），标准 B 树索引将被完全绕过。SQLite 将被迫执行顺序全表扫描，时间复杂度为 O(N)。

在全表扫描中：

  1. SQLite 将存储层中的每一行数据都读入内存。
  2. 查询引擎按顺序遍历文本的每个字节，逐个字符地比较，查找目标子字符串。
  3. 如果一封电子邮件正文包含 1500 个单词，而你有 2000 封电子邮件，那么 SQLite 会对每次击键操作逐字节地检查多达 300 万个单词！

此外，标准的 SQL LIKE 语句是“愚蠢的”：

  • 未进行分词：它无法识别单词边界。搜索“cat”会错误地匹配到“catalog”、“scatter”和“vacation”。
  • 未进行词干提取：搜索“optimize”会遗漏“optimizing”、“optimizer”或“optimized”。
  • 未进行相关性排序：搜索结果未加权；标题中的匹配项与第四段中的匹配项权重相同。

而 SQLite 的 FTS4（全文搜索 4） 引擎则改变了这一切。

解决方案：FTS4 和倒排索引的工作原理

SQLite 包含专用的全文搜索扩展（FTS3/FTS4 和 FTS5）。在 Android 的 Room 持久化库中，通过 @Fts4 和 @Fts3 注解原生支持这些扩展。

倒排索引：从 O(N) 到 O(1)

FTS4 不是在查询时扫描行，而是在插入时进行繁重的工作。

当 FTS4 对文本列进行索引时，分词器会将文本分解成单个单词（词元），规范化它们的大小写，去除标点符号，并构建一个倒排索引。

倒排索引本质上是一个词到文档的词典：

当你发出类似 MATCH 'benchmark*' 的搜索查询时，FTS4：

  1. 对搜索字符串进行分词。
  2. 在词元词典中执行即时查找。
  3. 获取包含该单词的完整文档 ID 列表。
  4. 返回记录，不扫描任何无关文本字节。

无论有 100 行还是 10 万行，查找操作都在不到一毫秒内完成。

主要观察结果

  1. 16 毫秒帧预算限制：处理 2000 封邮件时，SQL LIKE 查询耗时约 30.18 毫秒，超过了 60Hz 显示器约 16.6 毫秒的帧目标（120Hz 显示器约 8.3 毫秒）。处理 5000 封邮件时（约 63.76 毫秒），在 UI 线程或其附近执行 LIKE 会导致丢帧和明显的 UI 卡顿。
  2. 规模化下的性能分化：虽然 FTS4 在中小型数据集上能提供稳定的 1.6–2.3 倍加速，但到 5000 条记录时优势急剧扩大，执行速度比 LIKE 快 9.4 倍（约 6.81 毫秒对约 63.76 毫秒）。
  3. 前缀支持：FTS4 能够即时处理 arch* 查询，因为词元前缀可以直接在索引结构中遍历。

结论

SQL LIKE 是一个很棒的工具，可以用来创建原型或查询离散的编码列（例如状态码或简短标识符）。但是，一旦你的应用程序处理人类文本——消息、文档、笔记、产品目录——依赖 LIKE '%...%' 就会成为一个迫在眉睫的性能瓶颈。

通过将 Room 的 @Fts4 与 contentEntity 模式结合使用：

  • 你保留了清晰的关系型实体作为唯一可信数据源。
  • 你可以获得高性能的倒排索引查找，轻松扩展到数万条记录。
  • 你的用户界面依然流畅，充分尊重了用户的帧预算和电池续航。

如果你的 Android 应用包含用于查询文本字段的搜索栏，请不要等到生产环境中的数据集膨胀后才行动。立即迁移到 Room FTS，为用户带来他们喜爱的即时搜索体验。
