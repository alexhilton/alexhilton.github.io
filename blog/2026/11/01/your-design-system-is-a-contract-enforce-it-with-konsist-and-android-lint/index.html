用Konsist与Lint强制执行设计系统契约

Nov 1st, 2026 12:00 am

本文译自「Your Design System Is a Contract. Enforce It with Konsist and Android Lint」，原文链接https://proandroiddev.com/konsist-design-system-validator-jetpack-compose-d5c3814fe462，由Ravi Rawal发布于2026年10月21日。

本文将介绍如何在 Jetpack Compose 中强制执行颜色、间距、排版、形状和组件规范，并演示如何配合自定义 Android Lint 规则实现这一目标。

设计系统的可靠性取决于防止团队绕过它的规则的可靠性。

大多数安卓开发团队都有设计系统。

它们定义了字体、颜色、间距、形状、尺寸和可重用的 Compose 组件。
它们编写了使用指南，发布了组件库，并要求开发者遵循既定的规范。

然而，经过几个月的开发，同样的问题又开始出现了。

一个屏幕使用 16dp 的水平内边距；另一个屏幕使用 18dp。一位开发者创建了一个自定义文本样式，因为现有的字体看起来不太合适。

一项功能引入了一个硬编码的十六进制颜色值。一个按钮的圆角半径与应用程序的其他部分不同。有人创建了另一个卡片组件，因为现有的卡片组件似乎不方便重用。

这些决定单独来看似乎都不算特别危险。但它们结合起来，却破坏了设计系统原本应该提供的连贯性。

代码审查可以发现一些违规行为，但它并非可靠的强制执行机制。审查人员时间有限，规范容易被忽略，而且相同的反馈会在不同的拉取请求中重复出现。

更好的方法是将设计系统视为工程合同，并通过自动化检查来执行该合同。

对于使用 Jetpack Compose 的 Android 团队来说，Konsist 和自定义 Android Lint 规则可以互补地解决此问题。 Konsist 可以强制执行架构和结构规范。Android Lint 可以检查源代码中是否存在禁止的模式。Compose UI 测试可以验证最终界面在运行时的行为。

它们共同将设计系统规范从文档转化为可执行的规则。

首先要明确合同的实际含义

在编写测试或代码检查器之前，请确定你的团队希望每个功能遵循的规则。

并非所有设计系统规范都适用于同一种强制执行机制。有些规则涉及模块边界，有些涉及源代码表达式，还有一些涉及渲染后的界面。

Konsist 适用于结构约束。Lint 更适合检测禁止的源代码模式。运行时测试验证仅通过检查源代码无法确定的行为。

目标不是增加更多检查，而是将每条规则都放到执行层，以便能够可靠地进行检查。

使用 Konsist 保护架构边界

Konsist 是一个 Kotlin 架构测试库。它允许团队针对包结构、依赖关系、命名约定和其他源代码级架构规则编写测试。

当设计系统被拆分为公共 API 和内部实现包时，这种方法尤其有用。

这样做的好处是，架构决策可以执行。

同样的方法也适用于命名和包规范。

例如，一个团队可能需要：

  • 公共设计系统组件位于 designsystem.components 下。
  • Token 定义应放在 tokens 包内。
  • 特定于功能的 UI 组件位于其所属功能包内。
  • 内部实现类型遵循约定的命名规则。
  • 架构层保持其预期的依赖关系方向。

这些检查有助于防止结构漂移。

然而，存在一个重要的限制：包架构测试不会自动强制执行可组合组件内部的每种使用约定。一个功能可以仅依赖于已批准的包，并且仍然可以直接构造 Color(0xFF1769E0)。

这时，Android Lint 就派上用场了。

使用自定义 Android Lint 规则来捕获设计系统违规

Android Lint 会分析 Android 源代码并报告潜在的错误和问题。它还提供用于编写自定义检测器的 API。

对于设计系统而言，自定义 Lint 规则可以检查 Kotlin 源代码并标记违反团队约定的模式。

例如：

  • 在功能代码中使用数值字面量构建颜色。
  • 使用原始 sp 值而非已批准的排版角色。
  • 在需要标记的地方使用原始 dp 值设置间距。
  • 调用已弃用的设计系统 API。
  • 使用未经批准的组件实现。
  • 引用功能包中的内部设计系统符号。

每条规则都应该有明确的适用范围和清晰的失败信息。过于宽泛的规则如果会标记出所有合理的异常情况，就会造成不必要的干扰，最终导致开发者禁用这些检查。

具体检测器取决于应用程序如何对形状进行建模以及允许使用哪些 API。它还应该能够区分合法的自定义形状和意外重复的形状。

命名规则

命名规则通常可以通过 Konsist 来强制执行，尤其是在要求涉及包和类结构时。

例如，团队可以要求设计系统可组合体使用一致的命名约定，或者将实现类限制在内部包中。

规则应该反映团队实际采用的惯例，而不是仅仅因为命名限制容易自动化就强加这些限制。

强制组件重用，而不是仅仅强制使用 Token

集中管理的 Token 可以防止数值漂移，但无法保证组件行为的一致性。

考虑两个功能，它们都使用相同的间距和颜色标记，但各自实现了不同的按钮。一个功能能正确处理加载状态；另一个功能允许重复点击。一个功能具有预期的最小高度；另一个功能则没有。一个功能提供了适当的辅助功能语义；另一个功能则没有。

这两个功能虽然都能通过令牌检查，但仍然会呈现不同的用户体验。

使用 Compose UI 测试确保运行时正确性

静态分析可以识别源代码模式，但无法确定渲染界面的所有属性。

例如，Lint 规则可能会确认某个功能使用了 MaterialTheme.typography.bodyLarge，但它本身无法证明最终屏幕在大字体比例下仍然可读，也无法证明文本不会被其父布局裁剪。

Compose UI 测试应该涵盖这些运行时要求。

有用的测试目标包括：

  • 辅助功能语义和有意义的标签。
  • 支持的字体大小下的布局行为。
  • 启用、禁用、加载和错误状态。
  • 最小触摸目标要求。
  • 内容溢出和用户生成的长文本。
  • 交互行为和状态转换。

这将创建一个更完善的执法模式。

Konsist 检查架构边界。Lint 检测禁止的源代码模式。Compose UI 测试验证渲染行为。每一层都保护着契约的不同部分。

平稳落地规则，不影响交付节奏

如果一个代码库已经包含了多年不一致的 UI 代码，那么在第一天就将每条规则都变成阻塞性错误可能会导致大量的故障。

首先对现有代码库进行检查，了解违规之处。优先修复高价值案例，然后分阶段引入规则。

实际推广流程如下：

  1. 建立令牌和组件 API。
  2. 添加架构边界测试。
  3. 实现并测试一条自定义 Lint 规则。
  4. 对现有功能模块运行该规则，并评估误报情况。
  5. 修复违规或记录合理的例外情况。
  6. 将该规则设置为阻止新变更。
  7. 随着设计系统的完善，添加更多规则。

避免为了让持续集成（CI）通过而随意压制违规行为。例外情况应具体、合理且可审查。

此外，还应追踪违规次数、规则被抑制的频率以及哪些规则会产生误报。这些信息有助于区分有效的系统设计规范和一堆无意义的检查结果。

设计系统成为开发工作流程的一部分

这种方法的真正价值不在于团队编写了多少自定义规则。

这是责任的转移。

如果没有自动化强制执行机制，保持视觉一致性很大程度上依赖于开发人员对规范的记忆以及审核人员对偏差的发现。随着团队、模块和屏幕数量的增加，这变得越来越困难。

通过可执行规则，存储库本身可以传达哪些决策属于设计系统，哪些是合法的功能级选择。

开发人员仍然可以构建新屏幕，但屏幕必须遵守相同的架构边界，使用已批准的令牌，并遵循组织已建立的组件约定。

这在大型 Android 代码库中尤其有用，因为设计系统偏差通常会在各个独立功能团队之间逐渐显现。修复单个不一致的颜色或间距值的成本很小，但维护数百个略有不同的实现的成本却不低。

Konsist 和 Android Lint 并不能取代设计评审、用户体验评估或无障碍测试。它们只是从这些流程中移除了重复性的机械检查，以便评审人员能够将更多时间用于需要人为判断的决策。

这一原则不仅适用于 Compose 系统，也适用于更广泛的场景：如果一项约定重要到需要记录下来，并且足够精确需要描述，那么它可能也重要到需要自动强制执行。

设计系统不应依赖于每个人都记住约定。它应该让正确的路径易于遵循，并在意外违规行为进入生产环境之前将其暴露出来。
